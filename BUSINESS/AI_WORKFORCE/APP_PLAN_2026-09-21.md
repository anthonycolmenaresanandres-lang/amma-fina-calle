# AMMA Operations OS — AI Workforce App Plan

Status: REVIEWED PLAN — internal branch only, not production implementation.
Date: 2026-09-21

## Product decision

Do not build a separate standalone app from scratch.
Extend the existing Fina Calle Next.js application with a dedicated authenticated `/ops` area. Keep `/command-center` as the lightweight launchpad/index and link it to the Operations OS.

Reason: the repo already has Next.js 16, React 19, Supabase auth/admin-gating foundations, customer/client ledger work, internal APIs, Lead Arcade, and a live Command Center. Rebuilding auth, navigation, deployment and data access in another app would add duplication and maintenance.

## Critical correction to the current prototype

The present `/command-center` is private only by obscurity: unlinked + noindex. That is not sufficient for worker outputs, client data, Gmail-derived signals, financial state, or approvals.

The Operations OS must require authenticated admin access and fail closed. Reuse the existing Supabase admin-gating pattern only after verifying which migrations are actually applied. Do not assume prepared migration 0011 is live.

## Source-of-truth decision

Current GitHub `STATE.json` is appropriate as an experiment, not as the production operational database.

Production split:
- Supabase = live operational state, work items, workers, runs, handoffs, approvals, KPIs and audit events.
- GitHub = SOPs, prompt policies, versioned worker definitions, engineering evidence and immutable-ish documentation.
- Gmail/Calendar/GitHub/web = evidence sources through explicit tool adapters.
- ChatGPT Automations = temporary trigger layer during migration, not the permanent runtime.

## Agent runtime

### Current bridge
Keep existing ChatGPT Automations while the UI and database are built. Treat them as temporary external workers and ingest their verified outcomes manually or through controlled adapters.

### Target runtime
Use OpenAI Agents API for owned production workers once cost/tooling is approved.

Recommended topology:
1. One Executive Supervisor session receives a bounded business objective.
2. Supervisor delegates to specialized subagents only when needed.
3. Each worker receives a tool allowlist + authority policy + budget.
4. All durable outputs write to Supabase before the run is marked complete.
5. RED actions become approval requests instead of immediate tool calls.

This topology replaces a growing collection of unrelated scheduled reminders and avoids the 15-active-task ceiling.

## Tool layer

Do not assume ChatGPT-connected Gmail/Calendar/GitHub permissions automatically transfer to the custom app.

Build explicit adapters:
- Supabase: first-party operational store;
- GitHub: repo/SOP/CI evidence;
- Google Gmail/Calendar OAuth: later phase for sales/client evidence and approved sends;
- web search: current public evidence;
- Vercel/GitHub deployment actions: later, approval-gated;
- billing/payment data: separate high-risk adapter, read-only first.

Workers should never receive raw secrets. Server-side tool adapters own credentials and return minimal scoped results.

## Approval architecture

Default worker mode = PREPARE.

GREEN actions may execute internally.
YELLOW actions generate an escalation/work item.
RED actions generate an approval record.

For external sends:
worker drafts → approval card → Anthony reviews exact recipient/subject/body/attachments → approve → send service executes → provider message ID saved → stage updated.

Never treat button click as success until provider outcome evidence is stored.

## Security

- `/ops` requires authenticated admin session; no security-by-obscurity.
- RLS/default-deny on all ops tables.
- server-side service credentials only.
- tenant/client data segmented from public/internal marketing surfaces.
- prompt injection boundaries: retrieved text is evidence, not instructions.
- tool allowlist per worker.
- run budget, timeout, retry cap and concurrency cap.
- audit log is append-only from application code perspective.
- secrets never stored in prompts, run output or Git.

## Cost control

Every worker has:
- allowed models;
- max runtime;
- max subagents;
- max tool calls;
- per-run token/cost ceiling;
- daily/monthly budget;
- dry-run mode;
- stop-on-budget behavior.

`/ops` shows TODAY / MONTH cost and cost by worker. Expensive workers default to manual trigger until value is proven.

## What NOT to build in MVP

- no chat-first interface as the whole product;
- no autonomous external emailing;
- no auto-deploy;
- no automatic payments/refunds;
- no generic drag-and-drop agent builder;
- no multi-company SaaS permissions yet;
- no employee scheduling module folded into this project;
- no duplicated CRM beside Lead Arcade unless migration is explicit.

## Main integration with existing product

`/command-center` remains the map.
`/ops` becomes the cockpit.
`/lead-arcade` becomes or feeds the sales/pipeline visual layer.
`/customers` / existing client ledger feeds client views after auth/data boundaries are verified.
`OPERATIONS/AI_WORKFORCE/*` remains the policy/SOP source.

## Acceptance test for MVP

The app is successful when Anthony can open one protected screen in the morning and answer:
1. What are my top 3 company priorities?
2. What are my workers doing and did they actually succeed?
3. What revenue action needs me?
4. Which client/product issue is at risk?
5. What actions are waiting for my approval?
6. What did the AI workforce cost and produce?

If those six questions require opening Gmail, GitHub, Automations and several chats manually, the app has not yet achieved its purpose.

## Recommended next build

Do not start with agent execution.
Start with the authenticated Operations Mirror: schema + `/ops` dashboard + worker/run/work-item/approval views. Once the control plane is trustworthy, migrate exactly one agent into the new runtime.
