Everything in Park stays at zero net-new engineering; the four Quick-wins (menu fix, infra toggles, watchdog guards, landing decision) run in parallel as sub-day chores, not slots. Treat every doc-only skill and off-thesis personal project as harvest-or-archive, never as a build.

## Top-tier deep dives (Bet-now → Build-next)

### #1 · Fina Calle OS (AMMA canonical platform / Client OS)  —  Bet-now / Double-down
*State: **wip** · 7-axis (fit/rev/compl/effort/moat/risk/reuse): 5/3/4/4/3/3/5 · confidence: high*

A genuinely-shipped multi-tenant restaurant-modernization platform: one Next.js 16 + React 19 + Supabase app (live on finacalleos.com) serving owner portals (/owner/[id]), public QR menus (/m/[id]), a deterministic no-LLM "AI Request Desk", an admin request inbox (/customers/requests), and magic-link auth. Its core asset is an audited owner-write rail (apply_owner_change / apply_owner_size_price) — security-definer SQL with RLS, an editable-field allowlist, and audit-log-in-one-transaction — that every content edit flows through. Onboarding a tenant is literally inserting a restaurants + owner_emails row; the customer registry, menus, and audit are all live Supabase data, not mocks.

**Key risks:**
- Zero automated tests (no vitest/jest/playwright, no test files) on a codebase whose central logic is a 613-line deterministic triage parser and security-definer SQL that mutates live customer data — regressions are invisible and a parser miss can silently apply a wrong edit through the rail.
- Validated at N=1 tenant (Colattao only). Multi-tenancy is architected (restaurant_id everywhere, RLS) but never proven with a real second café; the headline 'onboard by inserting a row' is untested in practice.
- No monetization plumbing in the product itself — billing_status defaults to 'manual', no Stripe, plan is a free-text column. Speed-to-first-dollar depends entirely on out-of-band manual sales, not the platform.
- Onboarding and tenant creation are manual SQL with no admin UI; combined with the human 'send to AMMA team' fulfillment rail, the solo founder is the throughput bottleneck exactly where the thesis warns.
- Commoditized category: Toast/Square/Owner.com/BentoBox already ship QR menus + owner editing + ordering, often free-with-POS. The moat is the AI Request Desk + managed relationship/density, which is thin and unproven.
- Per memory, the premium /m/[id] public-menu template is deliberately held out of prod ('the vercel is the truth'), so the customer-facing menu shipped is the older template — the polished surface is on a branch, not live.

**Research it needs:**
- _(customer)_ Will a second, non-Colattao local café actually onboard and use the owner dashboard / Request Desk unaided — i.e. does the 'insert a row' multi-tenant claim survive a real second tenant?
- _(pricing)_ What is the monthly price and packaging (Starter/Pro tiers exist as a text column but no Stripe), and what is the willingness-to-pay among Virginia Beach independent restaurants for QR menu + owner self-edit + request desk?
- _(market)_ How many addressable independent food businesses exist in the Virginia Beach density target, and what is the realistic attach rate given QR-menu market saturation (Square, Toast, Owner.com, BentoBox already bundle this)?
- _(competitive)_ What is the defensible wedge versus Toast/Square/Owner.com/BentoBox, which already offer QR menus + owner editing + ordering — is the differentiator the AI Request Desk + AMMA managed service, and is that enough?
- _(operational)_ What is the cost/time of the AMMA-team manual fulfillment loop (the 'send to team' rail and SQL onboarding) per tenant, and at what tenant count does the lack of a self-serve onboarding/admin UI become the binding constraint?
- _(technical)_ Can the deterministic triage parser and SQL rails be covered by an automated test suite before more edit surfaces are added — there are currently zero tests on high-branching logic that mutates customer data?
- _(regulatory)_ For the billing/payments path that does not yet exist, what PCI/handling obligations and Supabase data-residency considerations apply once real customer payment or PII flows through the platform?

**Next action:** Prove the multi-tenant claim end-to-end: onboard ONE real second Virginia Beach tenant (insert restaurants + owner_emails, hand them the magic link), and in parallel add a minimal vitest suite locking the triage parser's apply/review decisions and the rail's allowlist behavior — before adding any new edit surfaces.

### #2 · Dual Perspective Newsroom  —  Bet-now / Double-down
*State: **shipped** · 7-axis (fit/rev/compl/effort/moat/risk/reuse): 5/2/4/3/3/2/3 · confidence: high*

A production-running, automated Instagram newsroom pipeline (Next.js/TypeScript, 1,336 files, ~58 services) that ingests local VBPD press releases + Google News RSS, clusters stories, runs an LLM verifier (gpt-5) for facts/legal risk and an LLM editorial writer (gpt-4o-mini) for prose, then deterministically anonymizes, gates, renders a 5-slide carousel, and publishes to Instagram via Meta Graph API. The LLM is prose-only; every safety/legal/anonymization gate is deterministic and runs post-LLM. It is the editorial automation engine behind Fina Calle and has confirmed at least one real live IG publish.

**Key risks:**
- Reliability: 29% of logged cycles failed and 14% needed review — too unreliable to sell as hands-off autonomous publishing without root-causing the scheduler/publish failure modes (matches the known scheduler-reliability issue).
- Single-tenant lock-in: hardwired to Fina Calle sources (VBPD + Google News) and Instagram-only; not yet multi-tenant, so it compounds slowly as a reusable OS module without real refactor work.
- Brand/legal: automated publishing of claims about named local people/incidents is inherently defamation/PII-exposed; safety gates are well-designed but legally unvalidated, and a single bad auto-publish damages the Fina Calle brand.
- Founder-bottleneck WIP: this plus VBFH are the two standout separate products competing for the same solo founder; running both as active builds violates the cap-WIP thesis.
- Local-scheduler dependency: production path runs on Anthony's Windows machine (Vercel cron deliberately off), which caps uptime and blocks a clean hosted-SaaS story.

**Research it needs:**
- _(operational)_ Why do 29% of cycles hard-fail and 14% land in needs_review (33 failed / 16 review of 114 logged runs)? Root-cause the failure classes (scheduler missed-window, public-URL stale-bytes, Meta API, render) before this can be sold as 'autonomous'.
- _(technical)_ What is the actual work to make the pipeline multi-tenant (per-city source sets, brand skins, separate IG accounts/tokens) so it becomes a reusable Fina Calle OS module rather than a Fina-Calle-hardwired single tenant?
- _(market)_ Is the buyer a local-news operator, an SMB marketing agency, or internal-only? Who pays for an automated local-IG newsroom, and is there willingness to pay vs. doing it in-house with Canva + a VA?
- _(regulatory)_ Defamation/PII exposure: the deterministic anonymizer and defamation_risk skip are good, but has a real legal review validated them for publishing claims about named local people/incidents at scale? data/ run payloads contain potential PII.
- _(competitive)_ How does this compare to existing local-news automation and AI social tools (e.g. generic schedulers + LLM), and what is the durable edge beyond Anthony's editorial-safety discipline?
- _(pricing)_ If productized, is it priced per-city/per-account SaaS or done-for-you service? What cadence/volume justifies the ~$1/mo LLM cost-base markup?
- _(operational)_ Vercel cron is intentionally disabled in favor of a local Windows scheduler — does that local dependency block selling this as hosted SaaS, and what does a reliable cloud scheduler migration cost?

**Next action:** Stop adding features and run a 2-week reliability hardening sprint: instrument and root-cause the 33 failed / 16 needs_review cycles (classify failure modes from .data/cron-responses + production-cron.log), fix the top failure class, and get a clean 14-day green publish streak before any productization or multi-tenant work.

### #3 · Digital Menu Module  —  Quick-win / Integrate
*State: **shipped** · 7-axis (fit/rev/compl/effort/moat/risk/reuse): 5/2/4/4/2/4/5 · confidence: high*

A shipped, data-driven public QR menu rendered at /m/[id] from Supabase by restaurant_id (Next.js 16 server component calling a get_public_menu RPC). It is the customer-facing read surface of a genuinely multi-tenant Fina Calle OS: a full schema (restaurants, categories, items, hours, promos), per-table RLS, generic per-id brand assets, and an audited owner write rail (apply_owner_change / apply_owner_size_price) so owners self-edit safely. One real tenant (Colattao) is seeded with a complete live menu.

**Key risks:**
- Commoditization: QR menus are a crowded, near-zero-price category; the menu alone has almost no moat or standalone revenue — its value is entirely as a hook/surface inside the OS bundle.
- Completeness gap found in code: item sizes are editable, stored, and shown in the owner dashboard and returned by the 0007 RPC, but the public /m/[id] page omits sizes from its type and does not render them — so Colattao's Large prices (e.g. Latte $6.50) are invisible to customers. Concrete, shippable bug.
- Zero automated tests in the entire APP/web repo; the security-critical audited write rail (apply_owner_change, RLS, security-definer functions) is unverified by any test suite.
- Onboarding is not yet productized: the one live tenant's menu was hand-authored into a SQL migration (0007), not entered via self-serve — so tenant scaling currently still funnels through the founder.
