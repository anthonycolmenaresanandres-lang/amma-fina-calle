## Safe local improvements made

1. Public intake now returns HTTP 503 plus `ok:false` when neither database nor email confirms receipt. Existing email-only fallback is preserved and labeled `email_only`; saved rows are labeled `saved`. UUID entropy is added to the timestamp reference. This does not add DB uniqueness or retry idempotency.
2. Request Desk previews carry a SHA-256 freshness fingerprint of owner email, tenant, original text, derived proposal and raw target data. Confirmation re-authenticates, re-reads and re-derives, then rejects a changed/missing fingerprint. File-bearing direct confirmations are rejected. This fingerprint is not a signature, authority token, expiry mechanism, or atomic database lock.
3. Partial/failed menu reads stop the preview and review-save flow rather than silently constructing a partial snapshot.
4. Recognizable ingredient/allergen/health claim keywords route free-text triage to human review. This is conservative keyword coverage, not semantic proof of safety, and does not change existing direct owner menu controls.
5. Review receipts distinguish a saved request from accepted/unconfirmed email notification. The UI no longer claims files were sent when it only proved they were saved. Notification failure never erases a saved request.

No execution policy was activated. Existing direct owner controls retain their current behavior. Local changes are preserved with the follow-up queue work in the isolated branch's local commit. See the follow-up approval package for the current implementation status.

## Minimal mobile-first target flow

Reuse the existing item picker. Keep one item per request and exact field choices; show category/name/size to disambiguate duplicate names. Default to a neutral field choice rather than a commercial price change. The owner sees:

1. **Choose item** — searchable existing items, including sold-out items. No implicit target inferred from a long brief.
2. **Choose change** — availability, display-name correction, description, price/size price, photo, or “Something else.” Each has its own validation and review rule.
3. **Review** — business/location, exact item and size, Current/Requested after values, affected guest destination, and whether this will be queued or needs review. Do not represent an LLM suggestion as the owner's confirmed instruction. Files remain pending until stored.
4. **Confirm request** — authenticate again on the server; use an idempotency key and immutable actor/tenant facts. Return the server UUID and short reference only after durable commit. Never clear an unconfirmed draft.
5. **Track** — request receipt, current status, last attempt/next retry, review reason, applied before/after and verified public result. Offer “Report a problem” and a separate owner confirmation of completion. A failed email is a delivery issue, not a failed request.

Use the existing typography and theme, a single column at 320/390 px, labeled native controls, clear keyboard focus, 44 px touch targets, wrapping values, and Current/Requested after on separate rows. No nested panels are necessary. Retain unsaved-draft warnings. Avoid persisting sensitive draft text/files into shared-device local storage by default.

## Minimal implementation sequence and acceptance criteria

### 1. Establish identity and structured requests — next approved database change

Before writing SQL, inspect actual deployed function definitions, policies, grants and migration state through authorized read-only access; do not assume source migrations were applied. Separate unverified public intake from owner submissions, even if both use the current table. Derive `actor_user_id` from `auth.uid()`, verified owner membership from server-controlled tenant mappings and confirmed email, and tenant/contact facts server-side. Check active membership and required password reset at sensitive RPCs. Owner role/capabilities must be explicit. Do not trust user-editable metadata or URL/tenant/contact fields supplied by clients.

Keep the existing UUID primary key; add unique reference and `(tenant_id, actor_user_id, client_idempotency_key)` constraints. Store exact entity UUID, bounded change type/field, typed before/after, expected version/hash, source kind, policy version, confirmation timestamp and approver identity. Public intake must not set verified owner attribution. Add row-level predicates for owners to read their own tenant requests and privileged operations to read only enrolled tenants. Revoke inherited PUBLIC execution where appropriate after impact review; do not broaden table/browser access.

Acceptance: anonymous submission cannot impersonate owner/tenant; owner A cannot submit, read, attach, approve or apply owner B's request; revoked/reset-required users fail closed; repeated submission returns the original ID; malformed/oversized/unknown fields fail; public registry/file exports remain unavailable. Test these against actual roles, not UI only.

### 2. Queue, delivery, and a human-reviewed pilot

Persist the request, first event and delivery outbox record in one transaction. Keep request state separate from delivery state. Suggested request states: `awaiting_owner_confirmation -> queued -> needs_review | ready -> applying -> applied_pending_verification -> awaiting_owner_ack -> completed`; branches include `conflict`, `failed`, `rejected`, `cancelled`, `rollback_requested`, `rolled_back`. Enforce allowed transitions server-side with actor/reason/time in append-only events. Never mark a request complete just because a notification was accepted.

Delivery outbox: request UUID, destination/config version, idempotency key, pending/leased/sent/retry_wait/dead_letter, attempt count, next attempt, lease expiry, provider reference and sanitized error category. Claim atomically using a lease; recover expired leases. Proposed bounded retries after 1 minute, 5 minutes, 30 minutes, 2 hours and 6 hours, then dead-letter for human action. Provider-supported idempotency plus request IDs protects a lost response. Limit attempts per drain. Retry notifications, never blindly replay content writes. Email should carry only reference, tenant label and a private inbox link; authenticate to read the brief or files.

A scheduler/worker is required for unattended retries. First verify whether an existing approved runtime can invoke a bounded drain inside current quotas without new billing. If none is available, use a manual authenticated drain and expose “retry pending”; do not promise autonomous retry. Do not couple this to the traffic-reporting task or purchase a worker/queue service.

Acceptance: saved request survives process exit; email timeout/rejection becomes retry state; lost responses do not duplicate requests; two drainers do not lease one job; lease loss recovers; poison requests stop; no logs contain contact details, free-text briefs, credentials or file URLs. Owners can see receipt and progress even if every notification fails.

### 3. Bounded execution — only after separate explicit enrollment and authority

Start with authenticated review and local preparation. Later, if Anthony authorizes it, permit one tightly bounded change type for explicitly enrolled tenants: temporarily mark a single existing item sold out (`is_available:true -> false`), with exact owner-confirmed preview and a verified public-menu publishing path. A display-name typo correction could be considered later under its own policy. Descriptions and arbitrary free text stay review-only initially. This is a proposed policy, not current authorization.

Enrollment record: Anthony's policy approval/version, tenant/location, verified owner UID, approved guest destination/data adapter, allowed operation/fields and limits, start/expiry, owner opt-in and confirmation requirements, rollback owner, revocation and kill switch. Confirm identity through an established channel before enrolling; an employee email, forwarded request, public contact form or third-party document cannot grant authority. Every execution rechecks active enrollment, original authenticated requester, current policy and revocation. Existing backlog gets no retrospective automatic authority.

| Change | Initial treatment |
|---|---|
| Temporary sold-out flag on one existing item | Candidate for future bounded execution after enrollment, exact owner confirmation and publication verification. |
| Name typo or ordinary descriptive copy | Human-reviewed content change initially; owner supplies exact replacement. Check ingredients/claims and meaning before considering a later narrower policy. |
| Prices, size prices, discounts, promotions, availability restoration, hours or commercial commitments | Explicit per-request tenant-owner approval and required Anthony/business review; no assistant-invented values. Existing manual owner self-service is separate. |
| Allergens, ingredients, diet/health/safety claims | Verified facts plus owner/team review; never autonomous under the initial policy. Keyword matches alone do not establish safety. |
| Payments, billing, access/security, credentials, privacy/exports, customer records | Separate authorized workflow; excluded from this executor. |
| Deletion, replacement, new items, bulk edits, schema/code/deployment or unrelated tenant changes | Human review, precise separate authority and recovery plan; excluded. |

Execution must use a narrow typed operation, never arbitrary SQL, shell text, browser instructions or instructions embedded in request content. Atomically lock/check expected revision, assert tenant/row/field/type, perform exactly one update, append a request-linked audit event and advance state in one transaction. Affected row count must equal one. Return conflict on mismatch. Store old/new typed values, actor UUID, reviewer/policy, request ID and executor version; redact private text from operational logs.

Read back both the authoritative record and actual guest destination. If publication is disconnected or readback cannot confirm, stop in verification-needed state. Owner receives the result through the portal and confirms completion. Rollback is a new audited inverse operation that checks the current value still equals this request's applied value/version; never overwrite a later owner's change. Failed rollback becomes human review. Revoke enrollment to stop future claims and disable the executor globally without deleting history.

Acceptance includes stale/conflicting edit, replay, duplicate workers, revoked tenant, invalid target, missing row, partial apply failure, unavailable guest site, rollback conflict, notification failure and malicious brief/file cases. No production autopilot before these checks and a reviewed tenant pilot pass.
