# Bodega owner pilot: local implementation and release decision

Prepared 2026-10-18 in `codex/owner-request-audit-20261017`, after local commit `2eec1aa`. Anthony selected **Bodega, availability and display order only**. This selection is not production activation, owner enrollment, schema approval or general permission to execute third-party instructions. This work remains local, with every release gate off by default. No push, deployment, live SQL, migration, grant, credential, real-owner enrollment, notification, paid service or autonomous production edit occurred.

## Assessment and minimal implementation

The initial [source-backed portal audit](OWNER_PORTAL_AUDIT_20261017.md) covers authentication, registry RPCs, intake, notifications, tenant permissions, audit history and missing executor. The [queue approval packet](OWNER_REQUEST_QUEUE_APPROVAL_20261017.md) and [account preparation report](OWNER_ACCOUNT_ONBOARDING_20261017.md) distinguish deployed-source behavior from prepared proposals. Their statements that no pilot was selected are historical: Bodega is now selected for this local continuation.

The decisive source gap is that `/demo/bodega` renders repository data, while the legacy owner menu rail writes `public.menu_items`. Updating a database item would not prove a Bodega guest saw the change. The smallest adapter therefore keeps Bodega's published source as the content authority and adds only versioned availability and order controls. No duplicate restaurant/menu/price rows, customer export, new service or new dependency are needed.

Readback is an assertion by a trusted service worker, not cryptographic protection against a compromised service principal. The deployment certificate binds source hash, deployed SHA, fixed origin/path, authority reference and expiry. The public control RPC exposes UUID/availability/order/version/source identifiers only, never account, contact, request or billing data. Raw private tables/helpers are revoked from anon/authenticated/service roles and protected by RLS; service operations are narrow security-definer RPCs.

## Requests reaching the assistant

The durable request queue and private operations inbox are the source of truth. Saved requests also create the central request record. The [prepared notifier](../APP/web/src/lib/owner/queue/notifications.ts) can send a fixed internal recipient metadata/private-link notice through existing mail infrastructure, with fenced durable leases, stable provider idempotency keys, six attempts and a 23-hour retry window; it is off and no send was attempted. Provider acceptance does not establish delivery, reading or assistant receipt.

Today the supported route is an Anthony-authorized Codex session using a verified authenticated read path to the private inbox/typed review RPC, followed by an explicitly authorized bounded action. There is no installed persistent assistant connection. A future recurring check/invoker requires separate permission, a successfully tested authenticated connector/read path, fixed tenant/type scope and a manual fallback. Do not repurpose traffic collection or imply an unattended local session will stay available. Existing/free-text/public/file requests remain untrusted data until authenticated and covered by Anthony's explicit authority. A new client cannot enroll itself or widen the policy by submitting instructions.

## Exact production approval scope, in order

1. **Code release, flags off:** integrate this branch with current main, including the separately deployed traffic-email changes, and rerun checks on that exact revision. Approve deployment of that reviewed result separately. This branch deliberately did not rebase, push or deploy. Confirm the canonical public origin and `VERCEL_GIT_COMMIT_SHA` availability; [Vercel system-variable documentation](https://vercel.com/docs/environment-variables/system-environment-variables) documents that variable and the project setting. No project setting was changed here.
2. **Database/schema/grants:** inspect actual deployed foundation/intake/admin/tracking schema and callers first. Independently approve a CLI-generated reviewed migration derived from the four SQL proposals above. `account_staging_v1.sql` and `ACCOUNT_STAGING_ENABLED` are **not required** for this first Bodega pilot. Shared queue core changes include hardening the existing `submit_change_request` signature and versioning all `menu_items` updates: review those impacts on all legacy writers/callers before release. Do not apply proposals blindly or assume local baseline equals production. Use an authorized nonproduction environment for hosted Auth/PostgREST/concurrency/advisor checks; no environment was provisioned here.
3. **Least-privilege grants:** public anon/authenticated control-snapshot RPC only; authenticated actor-scoped intake/status/acknowledgement; authenticated Anthony-only review; service-only bounded execute/rollback, get readback frame, record conflict and verify. Private schemas/tables/helpers receive no general read/write grant or public registry export. Reaudit the legacy registry/customer RPC predicates and inherited `PUBLIC` grants. Execute/notification grants alone do not activate settings or enroll owners.
4. **Real owner prerequisite:** privately identify the actual Bodega business owner, verify their business authority and confirmed Supabase Auth account with reset requirement cleared, verify exact tenant membership and obtain explicit consent. The earlier local access audit found a Bodega email mapping but no confirmed/reset-cleared matching Auth owner; this task did not query real Auth/customer rows again. A mapping or pilot choice is not enrollment. Human-led credential setup/recovery, if needed, requires its own approved process; no admin credentials were handled here.
5. **Publication baseline/certificate:** explicitly approve initial availability/order for all 50 mapped entries; the seed's `available=true` is a proposal, not knowledge of current stock. Approve exact source/deployment binding, fixed HTTPS destination, evidence reference and short certificate expiry. Enable publication only after actual guest readback passes. Execution and notifications remain off. Any content/ID/source/deployed-commit drift invalidates the certificate and requires fresh review.
6. **Bodega-only intake and policy:** explicitly approve `OWNER_REQUEST_QUEUE_TENANTS=bodega`, database `intake_tenants=['bodega']`, exact owner UUID and source manifest, availability/order only, policy/version, consent, expiry/revocation and Anthony's per-request reviewer role. No automatic approval, blanket content authority, legacy-request promotion, prices/commercial/allergen/health/payment/security/destructive edits. Owner confirmation is part of the workflow.
7. **Execution/caller separately:** only after the preceding checks, independently approve the protected invoker, service credential handling and cadence/manual operation; exact Bodega execution scope and both execution switches plus readback gate. No invoker is included here. Required app gates would be `BODEGA_MENU_CONTROLS_ENABLED=true`, `BODEGA_READBACK_ENABLED=true`, `BODEGA_EXECUTION_ENABLED=true` alongside scoped queue flags; database execution and certified enrollment must also pass. Do not set these as one blanket release action.
8. **Notifications separately:** approve the existing internal recipient, sender, scope/cadence and quota check before enabling mail app/database flags and `notification_tenants=['bodega']`. Sending clients a message requires explicit authorization; none is implicit in deployment/enrollment.

Pause execution first and stop its invoker if source/access/delivery is uncertain. Preserve queue/events for review; pause scoped intake/notifications/publication as appropriate. Removing an execution scope blocks approved pending work. Reconcile guest content before republishing; never bypass version conflicts or roll back over a later edit.

## Cost and remaining limits

No additional spending, packages, service, API model calls, infrastructure or subscription was introduced. One minimal public RPC per live page view uses the existing Supabase project; database requests/events and optional bounded notifications consume existing quotas. Current billing/capacity were not inspected, so zero marginal production cost is conditional on those quotas. Keep the manual authenticated path if unattended operation needs paid capacity. No income or availability guarantee is made.

This local preparation has no denied or uncertain production action: none was attempted. Remaining release dependencies are Anthony's scoped approvals above, actual owner identity/consent, deployed schema/grant audit, current-main integration, actual public deployment/source certification and an approved supported invoker/access path. Tests use synthetic fixtures and single-connection PGlite; they cannot prove hosted Auth session behavior or concurrent production roles. Browser evidence is Chrome mobile emulation, not physical Safari. Verification results and captures are in [BODEGA_PILOT_VERIFICATION_20261018.md](BODEGA_PILOT_VERIFICATION_20261018.md).
