# Disabled owner request queue — implementation and production approval package

This continues the [initial audit](OWNER_PORTAL_AUDIT_20261017.md). All changes are local on `codex/owner-request-audit-20261017`, based on `e0b44dd`. The SQL is an **unapplied proposal**, deliberately stored outside the migration directory. No live database, grants, credentials, email, deployment, subscription, scheduler or autonomous editor was changed. The traffic-report deployment remains separate.

## Bounded implementation

[`APP/web/supabase/proposals/owner_request_queue_v1.sql`](../APP/web/supabase/proposals/owner_request_queue_v1.sql) implements the database behavior exercised in synthetic in-memory tests:

- **Attribution hardening first:** replaces the existing `submit_change_request` signature. Tenant-less public inquiries remain possible and are explicitly `public_unverified`. A caller claiming a tenant must have a verified Auth user ID, a confirmed email, no mandatory-reset flag, and that tenant's `owner` mapping. Business/contact/source attribution is derived from Auth and the registry rather than supplied fields. Historic rows are not retrospectively trusted. Identity rows are held stable for each sensitive transaction.
- **Authenticated queue:** server UUID/reference, owner UID and email, exact item/type/value/revision, original brief, confirmation timestamp and unique `(tenant, owner UID, client key)`. Retries with the same payload return the original receipt; reusing the key for different content fails. Request + event + notification job commit together, or none commit.
- **Independent gates:** database intake/execution/notification settings all default `false`; application intake requires `OWNER_REQUEST_QUEUE_ENABLED=true`, and notification delivery additionally requires `OWNER_REQUEST_NOTIFICATIONS_ENABLED=true` plus existing mail configuration. There are no seed enrollments. Missing settings fail closed.
- **Review before execution:** each executable request needs authenticated Anthony authority review, an active enrollment tied to that owner UID and policy version, owner confirmation, an exact connected source and unexpired approval. No free-text interpretation grants authority. `name_typo` and general `review` requests cannot become executable under this implementation.
- **Atomic conflict protection:** a version trigger covers every menu-item update, including existing manual rails. A queued apply locks/checks the original owner/policy/item and expected revision/value, updates one bounded field, and appends a request-linked audit record and event in one transaction. Missing/stale targets do not produce false successful audit records. Single-item sort positions are bounded to 0–10,000, serialize queue order edits by category, and refuse occupied positions; there is no bulk reorder or automatic shifting.
- **Completion and rollback:** apply stops at `awaiting_verification`; a trusted verifier must attest to the approved public path/value while the authoritative revision still matches. The original owner then confirms completion. Another edit before acknowledgment produces `completion_conflict`. Owner-requested rollback restores only this request's old value if the applied revision/value is still current; otherwise it becomes `rollback_conflict`. Rollback also requires public verification and can be acknowledged by the owner. No history is silently rewritten.
- **Durable outbox:** leased, fenced claims; expired-lease recovery; maximum six attempts with waits of 1 minute, 5 minutes, 30 minutes, 2 hours and 6 hours; fixed error categories; dead-letter state. A 23-hour retry cutoff stays within the provider's documented 24-hour idempotency retention. The same outbox ID supplies the provider key. This is bounded at-least-once processing, not a promise of exactly-once inbox delivery. [Resend's idempotency contract](https://resend.com/docs/dashboard/emails/idempotency-keys).

[`queue/client.ts`](../APP/web/src/lib/owner/queue/client.ts) validates bounded payloads and omits caller-supplied identity. [`queue/actions.ts`](../APP/web/src/lib/owner/queue/actions.ts) re-authorizes owners and checks the selected tenant before completion/rollback acknowledgment. [`queue/notifications.ts`](../APP/web/src/lib/owner/queue/notifications.ts) provides a default-off manual drain with an 8-second attempt timeout, one notice per batch by default and at most ten if explicitly selected. It sends only fixed metadata and a private inbox link to the configured operations address. No client brief, file link, owner address or raw provider error enters notices/logs. All network calls in tests are mocked.

The existing Request Desk switches to review-only queued submission **only if the app flag is explicitly enabled**. It preserves a client key across uncertain retries and avoids an in-memory mail attempt for a queued receipt. Direct Request Desk apply is blocked in queue mode. With flags unset, the existing flow remains in use. Existing direct owner menu controls remain a separate manual self-service path; their changes invalidate queued revisions.

## What this does not activate or finish

No API route, cron, webhook, listener or background process invokes the notice drain or executor. There is no new paid runtime or queue service. Pending retries need a separately approved invoker; until then they remain durable pending work. Structured submission and completion action APIs are prepared, but their full owner-facing status/confirmation screen is not wired into the portal yet. The existing inbox continues to show mirrored status and receipt references.

The public-verification RPC checks a **trusted service assertion** against the approved path, typed value and current database revision. It does not fetch or inspect a live website itself. No HTTP publishing/readback adapter was provisioned, and no live menu source has been certified by this task. Its tests use synthetic readback assertions. Connecting a verifier and owner status UI is a release prerequisite, not an already-working production capability.

The legacy public attachment-metadata RPC remains a separately identified hardening item. Files and free-text briefs are untrusted data; this executor never interprets them or turns them into code/SQL/authority. The original scalar owner rail's missing-target audit flaw remains outside the new queued rail. Direct manual owner editing is not made atomic merely by adding the queue. These limitations must be included in release review.

## Exact policy choices

1. **Recommended first pilot: availability only.** One existing item and exact boolean state, owner-confirmed before/after, active source-certified enrollment, Anthony approves each request, no files interpreted, atomic apply/readback/owner acknowledgment. Begin with temporary sold-out changes. Restoring availability requires an equally explicit reviewed request; it is not inferred from inventory or a message.
2. **Optional next pilot: availability plus one item's display-order value.** Add `display_order` to that tenant's approved types only after real public ordering/tie behavior is verified. No category moves, bulk sorting, renumbering or collision resolution. A collision becomes review/conflict.
3. **Typos: review and local preparation only.** Store `name_typo` requests with exact before/after. The code intentionally rejects approval for execution of this type. A later, narrower implementation and separate approval would be needed to automate names; the assistant cannot prove a replacement does not change an ingredient, allergen or commercial meaning from the word “typo.”

Prices/size prices, discounts, ingredients/allergens/health claims, photos, deletion/new items, hours, payments/accounts/security, customer data/exports and deployments are excluded. They require separate explicit review and authority. Enrollment never converts historic public requests or third-party instructions into authority.

Every enrollment needs: confirmed tenant/location and immutable owner UID; current verified email and `owner` mapping; Anthony's approval reference and policy version; owner consent timestamp; permitted exact operation types; expiry/revocation; the actual approved guest path; data-source kind; dated source/readback evidence; and the person responsible for verification/rollback. There is no self-enrollment RPC or seed enrollment. Access/credential provisioning remains a separate human action if required.

## Database and security approval package

This is **not authorization to apply the proposal**. Required approvals/checks before production:

1. Inspect the actual deployed schema, roles, function definitions, Auth schema, owner role values, existing migration history and private-schema exposure. Test existing owner sign-in/request compatibility. The new owner path deliberately requires the `owner` role; do not silently rewrite manager/staff mappings. Existing logout/session-token semantics are not replaced by a new session-revocation system.
2. Review the SQL's five private RLS tables (`settings`, `enrollments`, `requests`, `events`, `outbox`), indexes, five added public-table columns, request/history foreign keys and item-version trigger. The retained references can block destructive item/tenant deletion; deletion/retention needs its own reviewed process. There are no automatic cleanup/deletion jobs.
3. Review privileged function ownership and empty search paths. Private schema/tables/sequences/helpers lose direct PUBLIC/anon/authenticated/service-role access. Five narrow public owner/admin RPCs receive authenticated EXECUTE: submit, inspect the immutable authority-review payload, authority review, owner acknowledgment and own-request status. Five worker RPCs receive service-role EXECUTE only: execute, verify, rollback, notice claim and notice finish. PUBLIC/anon EXECUTE is explicitly revoked for all new entry points. The existing legacy intake retains anon/authenticated EXECUTE but now authenticates any tenant claim. These are proposed permission changes requiring explicit production approval.
4. No Supabase CLI was available here. After review, use the CLI's documented `migration new` command to generate a fresh, unused migration and copy the reviewed proposal into it. It is intentionally not in `supabase/migrations`; no migration history entry or database change happened here. Run security advisors, role tests, rollback/backup review and real two-session concurrency tests in an approved environment before application. PGlite's single connection cannot prove live concurrency or production RLS/default-grant behavior.
5. Apply only after explicit approval, initially leaving all DB settings `false`, all app flags unset and enrollments empty. Smoke-test anonymous tenant spoof rejection, owner A/B isolation, confirmed/reset-required users, legacy tenant-less inquiry receipt and private registry/files. Verify no client-side service key or public customer export appears. Review/harden the legacy attachment metadata route before anyone treats uploaded context as authenticated evidence.
6. Release the owner status/confirmation UI and a trusted public-source verifier under separate validation. Certify one tenant's real destination, not a synthetic `/m` route. Record the enrollment/approval/owner consent without storing credentials.
7. Enable **intake only** after its release review: app intake flag and DB `enabled`; execution/notification flags remain false. No fallback to legacy intake is used if an enabled queue cannot save. Review request IDs, retries, attribution, private status/history and pending notification state.
8. Only after an approved operations recipient, existing configuration/quota/runtime and a specific notification test are confirmed may notification flags and a bounded invoker be enabled. No invoker is supplied/activated here. Provider acceptance is not delivery or assistant receipt. Do not reuse the traffic task's send schedule or branch.
9. Only after exact policy + tenant enrollment + public verifier + owner confirmation UI approval may execution be enabled. Anthony still approves each executable request in this version. A request's existence, an email wake-up or a model classification is never that approval.

Stop/pause: set execution/notification DB gates false and stop the approved invoker; unset app flags to return the Request Desk to its existing mode. Preserve queue/history. Do not roll back the attribution fix by restoring the vulnerable RPC. A content rollback uses the fenced inverse operation and verified public readback; later revisions cause conflict and human review. Recovery of an uncertain email after the retry window needs explicit review rather than a new automatic provider key.
